Treat it like SSH

Treat access to Pelican like SSH access: it can read your sessions and run Claude Code, and so commands, as you.

  • Every browser signs in, also on this computer. Pelican listens on 127.0.0.1 and asks for the access token in the link it prints, or for your password, so other accounts and programs on the computer get nowhere. The token is random and kept readable only by you; the password is set on the computer itself and kept as a scrypt hash. A phone signs in with a QR code that works once, for two minutes, and never sees the token or your password. Failed sign-ins are limited to 10 per client and 30 in all every 10 minutes.
  • Cookies are HttpOnly and SameSite=Strict, signed with a secret that changes with the token or password. A browser in use stays signed in; 30 days without use sign it out. Signing out signs it out on the computer too: its cookie is refused from then on, also after a restart, and its terminals and live updates close at once, in every tab.
  • Only Pelican’s own page. Its requests carry a header another site cannot add, requests a browser says come from another site are refused (reads too), and changes must come from Pelican’s origin or one you allowed. The server answers only to this computer’s names, loopback, *.ts.net and the names you configure (DNS rebinding), and only Pelican’s own origin may frame it.
  • What Claude writes stays on the screen. Images in a reply load only from Pelican. Pages and visuals Claude makes show as still pictures in a sandboxed frame; when you tap Run, their scripts run in a frame of their own that cannot reach Pelican and talks to no server but the public script and font CDNs.
  • Folders run nothing of their own until you trust them. See Folders you trust. Where git runs for Changes, it runs without hooks, the file-system monitor, external diffs, diff drivers, text converters or a pager, and fetches nothing.
  • A terminal is your shell, as you. It opens under the same checks as the rest of Pelican, runs in a folder as Claude Code does there, gets none of Pelican’s settings, and lives in memory only: at most 10, ended with Pelican. Nothing runs in one without you: Run in terminal asks first, showing the whole command, only in Claude’s replies and on its own steps and your ! commands (never one you denied, nor a subagent’s or a workflow’s), and for a command with nothing hidden in it or laid out out of sight, a paste cannot run without Enter, a new token or password closes it on every browser, signing out closes it in that browser, and Claude sees a terminal only in what you quote. Its native part is Microsoft’s node-pty, file for file, which CI checks for every platform, with the few lines of its own as read for its version and nothing that runs as it installs.
  • An update installs only Pelican, from npm, when you ask. Pelican asks the registry a global install uses, never one a project’s .npmrc names, for pelican-cc’s newest version, and reads its changelog from the package, downloaded from that registry alone, within set limits, and checked against the registry’s integrity. Update takes a signed-in request from Pelican’s own page, one at a time, never in a demo, for exactly the version the registry named; npm installs it with its integrity checks and no package scripts, only where npm itself put Pelican, and Pelican never runs sudo. SECURITY.md lists each command it runs.
  • What gets installed is what was tested. The packages Pelican uses are built into it, as CI tested them; the Agent SDK, with the Claude Code it brings for your computer, and the terminal’s native part, for your computer too, are each pinned to one version.
  • --no-auth is for when something in front of Pelican authenticates. The demo signs no one in, so it stays on 127.0.0.1 unless you pass it.
  • No copies. Pelican reads Claude Code’s transcripts where Claude Code writes them, and saves a ! command’s output too long for the conversation where Claude Code saves one, in the session’s tool-results folder, readable only by you. It stores uploads, push keys and subscriptions, the sign-ins signed out until their cookies would have expired, the folders you trusted, the folders in the system’s temp folder you started sessions in, and which sessions you pinned or archived in its state folder, keeps terminals in memory only (a command Run in terminal runs is written for its shell to read, readable only by you, and removed with its terminal), and sends nothing anywhere but your browser and, for notifications, your browser’s push service.

The whole model is in SECURITY.md. Report a vulnerability privately through GitHub security advisories.
